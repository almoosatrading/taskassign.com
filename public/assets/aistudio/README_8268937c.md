# HR Tasks — AlMoosa Trading Company

An internal, bilingual (English/Arabic) task assignment and tracking application. Managers assign tasks to their direct reports; employees track, update, and complete them; administrators manage the employee directory. Built from the attached "AI Coding Agent Instruction" specification.

This is a working application with a tested backend, not a static mock-up — see [Verifying this yourself](#verifying-this-yourself) for exactly what's been run and confirmed.

## Tech stack

**Backend:** Node.js, Express, TypeScript, PostgreSQL via [Drizzle ORM](https://orm.drizzle.team), JWT access tokens + rotating refresh tokens in httpOnly cookies, Zod validation, Jest + Supertest for integration tests.

**Frontend:** React, TypeScript, Vite, React Router, `react-i18next` for bilingual/RTL, Tailwind CSS.

**Why this stack:** the spec asked for a stack to be proposed before building. Express/Postgres/React is a boring, well-understood combination for an internal CRUD-plus-workflow tool — nothing here needs a more exotic stack, and "boring" means whoever maintains this next won't need to learn something unusual first.

## Why Drizzle instead of Prisma

This started as a Prisma schema. Prisma's `generate` step downloads a native query-engine binary from `binaries.prisma.sh` at build time; the build environment this was developed in couldn't reach that host, and rather than work around it by pulling a precompiled binary from an unofficial mirror, the data layer was rewritten against [Drizzle ORM](https://orm.drizzle.team), which is pure TypeScript and talks to Postgres directly over `pg` — no separate binary to fetch, ever.

That turned out to matter for a second, better reason: this is an **internal** tool, plausibly deployed behind a corporate firewall that may not allow egress to arbitrary third-party hosts either. Not depending on reaching `binaries.prisma.sh` (or any single external host) to even build the backend is a genuine operational advantage here, not just a workaround for the environment this was built in.

## Local development

Prerequisites: Node.js ≥ 18, Docker (for Postgres) or a local Postgres 14+ instance, npm.

```bash
# 1. Install everything (root workspace covers both backend and frontend)
npm install

# 2. Start Postgres
docker compose up -d

# 3. Configure environment
cp backend/.env.example backend/.env
cp frontend/.env.example frontend/.env
# Edit backend/.env: set JWT_ACCESS_SECRET and JWT_REFRESH_SECRET to real
# random values, e.g.: openssl rand -base64 48

# 4. Apply the schema and load development-only sample data
npm run db:migrate --workspace=backend
npm run db:seed --workspace=backend

# 5. Run both apps (backend on :4000, frontend on :5173)
npm run dev
```

Sign in at `http://localhost:5173` with any of the seeded accounts (see the table printed by `db:seed`, or `backend/src/db/seed.ts`) — all share the password `DevPass123!`. These are fictional accounts for development only; see [Database](#database).

## Environment variables

Every variable is documented inline in `backend/.env.example` and `frontend/.env.example`. The ones you must change before anything beyond local dev:

| Variable | Why it matters |
|---|---|
| `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET` | Session security. Generate with `openssl rand -base64 48`; never reuse the example placeholder, never commit real values. |
| `COOKIE_SECURE` | Must be `true` once served over HTTPS (required in any real deployment). |
| `DATABASE_URL` | Points at your actual Postgres instance. |
| `CORS_ORIGIN`, `FRONTEND_URL` | Must match wherever the frontend is actually hosted. |
| `COMPANY_TIMEZONE` | Drives every deadline/timestamp the UI shows — see spec requirement on a consistent, company-wide time zone. Defaults to `Asia/Riyadh`. |

## Database

Schema lives in `backend/src/db/schema.ts` (the single source of truth); `backend/drizzle/migrations/` holds the generated, committed SQL. To change the schema: edit `schema.ts`, run `npm run db:generate --workspace=backend` to produce a new migration file, then `npm run db:migrate --workspace=backend` to apply it.

**Seed data** (`npm run db:seed --workspace=backend`) is fictional and clearly marked as development-only in the script itself — no real employee data or production credentials, per the spec. It also sets `mustChangePassword: false` on every seeded account purely so you can explore the app immediately; every account created for real through the Employee Directory defaults to `mustChangePassword: true` and forces a change on first sign-in.

**Admin bootstrap and recovery:** seed data is dev-only, but every other account is created by an already-authenticated Administrator through the app — a brand-new production database has neither. `backend/src/db/create-admin.ts` is an operator-only CLI tool. It creates the first admin by default; creating an admin in a populated database requires `--allow-existing-users`. To explicitly recover an existing account, pass `--reset-existing` and its email; it sets that matching account to active Administrator, resets its password, revokes its sessions/reset links, and requires a password change at next sign-in. Passwords must be supplied through the process environment, never as a command-line argument or committed file.

```bash
npm run db:create-admin --workspace=backend -- \
  --name "Your Name" --employee-id "EMP-0001" \
  --email "almoosatradinghrd@gmail.com"
```
For an existing account, run the same command with `--reset-existing --email "almoosatradinghrd@gmail.com"`; `--name` and `--employee-id` are optional in recovery mode and the existing values are preserved. Set `ADMIN_BOOTSTRAP_PASSWORD` in the process environment using your hosting platform's secret manager before running it; avoid putting real passwords in shell history or source files. For PowerShell, set `$env:ADMIN_BOOTSTRAP_PASSWORD` for the process, run the command, and then remove it with `Remove-Item Env:ADMIN_BOOTSTRAP_PASSWORD`.

## Running the tests

The suite covers exactly the things the spec calls out as acceptance criteria: role-based access control, cross-employee task/attachment privacy, manager assignment scope, and notification triggers. It runs against a real Postgres database (not mocks), because the authorization logic lives partly in actual SQL `WHERE` clauses and a mock would let a bug in those clauses pass silently.

```bash
# One-time: a dedicated test database (never point this at dev or prod data —
# tests TRUNCATE every table before each test)
docker exec -it <postgres-container> psql -U hrtasks -c "CREATE DATABASE hrtasks_test OWNER hrtasks;"

cd backend
DATABASE_URL="postgresql://hrtasks:hrtasks_dev_password@localhost:5432/hrtasks_test" npx tsx src/db/migrate.ts
DATABASE_URL="postgresql://hrtasks:hrtasks_dev_password@localhost:5432/hrtasks_test" npm test
```

33 tests, all passing as of this writing, covering:

- **Auth** (`tests/auth.test.ts`) — login/logout, generic errors (no user enumeration), deactivated accounts, forced password change gate, session revocation.
- **Task privacy** (`tests/task-privacy.test.ts`) — an employee requesting another employee's task by ID gets 404 (not 403 — confirming existence is itself a leak), the attempt is audit-logged, and admins get no implicit access to task content.
- **Manager scope** (`tests/manager-scope.test.ts`) — a manager cannot assign tasks to another manager's reports, to another manager, or to a deactivated former report.
- **Notifications** (`tests/notifications.test.ts`) — assignment and completion each notify the right person, and a user cannot mark another user's notification read.
- **Attachments** (`tests/attachments.test.ts`) — upload/download authorization mirrors task authorization exactly, including by direct ID manipulation; disallowed file types are rejected.

## Security model

The short version of how authorization is enforced (details in `backend/src/services/task.service.ts` and `middleware/`):

- **Every check happens server-side, in the database query itself**, not just in what the UI chooses to render. An employee's task list is generated with `WHERE assigned_to_id = <their own id>` — there's no code path where "all tasks" are fetched and then filtered.
- **Out-of-scope access returns 404, not 403.** Confirming "this task exists, you just can't see it" is itself information you shouldn't have.
- **Sessions are a short-lived JWT access token plus a rotating, database-backed refresh token**, both in httpOnly cookies. Deactivating an employee or changing their role immediately revokes their refresh tokens — they don't just quietly lose access once their current access token expires up to 15 minutes later.
- **Passwords** are hashed with bcrypt (cost 12), never logged, never returned by any API response. Password reset tokens and refresh tokens are stored as SHA-256 hashes, not the tokens themselves — a database read alone can't be replayed as a live session or reset link.
- **File downloads** re-derive authorization from the attachment's own task on every request (never trust a client-supplied claim), and are always served as `Content-Disposition: attachment` regardless of file type, so an uploaded HTML/SVG file can never render inline in the app's own origin.
- **Audit log** (`audit_logs` table) records logins, failed logins, task lifecycle events, employee record changes, and denied access attempts, each tied to the acting user where there is one.

## Bilingual / RTL support

English and Arabic have full, independently-verified key parity in `frontend/src/i18n/{en,ar}.json` (140 strings each, checked programmatically — see the build log). Language is user-selected, defaults to English for new sessions, persists per-browser, and switching sets `<html dir>` live, which (combined with CSS logical properties throughout — `start`/`end` rather than `left`/`right`) flips the whole layout, not just the text. Dates and times are rendered via `Intl.DateTimeFormat` with the configured company time zone and the active UI locale, so a deadline reads correctly however the viewer has their device set.

## Deployment

The two Dockerfiles (`backend/Dockerfile`, `frontend/Dockerfile`) and `docker-compose.prod.yml` are a reference starting point, not a turnkey production manifest. Before going live:

- Put a real reverse proxy / load balancer in front of both (TLS termination; neither container does HTTPS itself). Set `COOKIE_SECURE=true` once that's in place.
- Match the upload size limit in three places: `MAX_UPLOAD_SIZE_MB` (backend env), and your reverse proxy's body-size limit (e.g. nginx `client_max_body_size`) — a proxy with a smaller default than this app's will reject large uploads before they ever reach it.
- Mount `/app/uploads` (backend container) to persistent storage, or point `storage.service.ts` at object storage instead — see [Known limitations](#known-limitations--read-before-production-use).
- Generate real `JWT_ACCESS_SECRET` / `JWT_REFRESH_SECRET` values; never reuse anything from `.env.example` or from local dev.
- `VITE_API_URL` is baked into the frontend at **build** time (Vite inlines env vars), so pass it as a Docker build arg pointing at your real API URL, not a runtime environment variable on the running container.

## Known limitations — read before production use

The spec explicitly asks for honest scoping here rather than silently omitted requirements. Before handling real employee data:

- **Malware scanning on uploads** is a documented extension point (`storage.service.ts`), not implemented — there's no credential-free way to stand up a real antivirus integration. Wire in ClamAV or a cloud AV API there before accepting untrusted uploads in production.
- **WhatsApp sharing** uses `wa.me` share links (opens the sharer's own WhatsApp with a pre-filled message containing only a task title and a login-gated link — never task content), which the spec explicitly permits without any API credentials. The official WhatsApp Business Platform integration is a stubbed, documented extension point (`whatsapp.service.ts`) if you need server-side send confirmation later; it requires a Meta Business account this project can't provision for you.
- **Email notifications** are optional per the spec and off by default; configure real SMTP credentials (`EMAIL_ENABLED=true` + `SMTP_*`) to turn them on. Without that, password reset links are logged to the server console instead of emailed — fine for development, not for production (`EMAIL_ENABLED` should always be `true` in production).
- **Manager "reporting scope"** is implemented as direct reports only (one level), which is the most defensible reading of the spec without a documented multi-level hierarchy requirement. If AlMoosa's org chart needs a manager to see their reports' reports too, that's a scoped change to `task.service.ts`'s `assertEmployeeInManagerScope`.
- **No frontend automated tests.** The spec's acceptance criteria are specifically about server-side authorization (role enforcement, task/attachment privacy, assignment scope, notifications) — all covered by the backend suite. The frontend has been type-checked, production-built, and manually smoke-tested end-to-end (real cross-origin login, cookie, and CORS flow against the real API — see below), but has no automated UI test suite.
- **Dev-tooling dependency advisories:** `npm audit` is clean (zero vulnerabilities) for both backend and frontend **production** dependencies. A handful of moderate/high findings remain in dev-only tooling (Jest's coverage chain, Vite's bundled dev-server esbuild) that never ship in either production build; the Vite one specifically only matters while `vite dev` is running locally. Worth revisiting on your own schedule, not urgent.
- **Rate limiting** on auth endpoints is a simple in-memory, per-IP limiter — adequate for an internal tool on a corporate network, not sized for a public-facing deployment with many users behind one NAT'd IP.

## Admin guide

- **Roles** are a capability, not a job title: `ADMIN` manages the employee directory only (and, by design, has no default access to task content — see [Security model](#security-model)); `MANAGER` can create tasks and assign them to their own direct reports; `EMPLOYEE` sees and acts on only their own assigned tasks.
- **Deactivating** an employee (Employee Directory → the user-x icon) revokes their access immediately and keeps their historical tasks intact — nothing is deleted.
- **Changing a role or manager** forces that person to sign in again (their current session is revoked) so the change takes effect immediately rather than at next natural token expiry.
- **Temporary passwords**: when you create an account, share the temporary password with that person through a secure channel (not email in plaintext, ideally) — they're required to replace it before they can do anything else in the app.
